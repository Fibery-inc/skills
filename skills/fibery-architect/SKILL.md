# Fibery architect

Turn how a team works into a Fibery Space they'll run their work in: about 80% of what a mature Space would have, which is enough to run the process tomorrow and small enough to still feel like theirs, shaped to their words and their workspace. You read the process (from the person, a document or an existing Space) and the workspace it will live in, ask what only the person can answer, then design the Space and build it with Fibery MCP straight away: their answers are the go-ahead, and a short report after the build says where to start and what's left to them. A Space that exists, just built or one the team already runs, is changed the same way when the person asks (`references/change.md`): read, said in a few lines, done; only a change that would lose or rewrite the team's data waits for a yes.

## What you need

- **Fibery MCP, connected to the target workspace, with `execute_code`.** The target is the connected workspace unless the person names another; then that one must be connected instead. The build runs as scripts through `execute_code`; if the connected server doesn't have it, say that this build needs it and build nothing.
- **Only the tools you call directly**: `execute_code`, `get_spaces` and `get_databases`, `replace_document_blocks` and `fetch_view_data` for the guide, `query`, `update_formula_field`, `update_automation` and `create_view` for repairs, and when needed `get_fibery_skill` (an app's guide) or `fetch_by_url` (a linked Fibery document). Every other Fibery tool is called inside a script, where it needs no loading, and the templates in `references/build.md` and `references/change.md` show its input; in a client that loads tools on demand, loading them all would add about 25K tokens to every turn. In a client that loads tools on demand, load the first nine in one search, with one Fibery connector's prefix when two are attached, and `get_fibery_skill` with them when the design has an app: it is the one Fibery tool a script can't call. Load any other tool only when a call to it fails and its error doesn't say what it wants.
- **A working folder** for `design.md`, when you can write files.

Paths are relative to this skill's folder. What to read, and when:

| File | Read it when |

| `references/build.md` | before the questions too, so the build starts the moment they're answered: the six scripts in order, each with its rules, its template and its traps |

Read it as soon as the design you are writing, or have written, has an app, a map, a gallery, a timeline, a database nested in itself, a form's other defaults, a view or rule on one option or record, or a metric or table tab, before `design.md` is finished, since these shape the design; and when you repair a failure or a script fails |

Read each file whole with the file-reading tool, not a shell command; when a read comes back cut off, read the rest before going on. Read what the build needs before the questions, in one message: the design guide, the example and `build.md`, so it starts the moment the person answers. A change reads `change.md` and `build.md`, and nothing else unless the change adds a process, which needs the design guide too. A question (§1) needs the design guide alone; the rest is read once they ask for the build.

## 1. Understand the process

| The person gives you | Do this |
|---|---|
| An idea ("set up our hiring process") | Ask only the questions whose answers change the structure (§3): usually the stages and the roles. If they said "just build it", ask nothing. |
| A request to be interviewed, or a vague idea | The design guide §1: a few questions at a time, in their words, playing the model back before you design. |
| A process document, SOP or notes | Read it fully before asking anything; the design guide §1 table says what each part of it becomes. |
| An existing Fibery Space (theirs or another workspace's) to copy or improve | Read it with the script in `references/change.md` §1, then design a new Space from it, copied or improved as asked; the existing Space is never changed. |
| A change to a Space that exists, or "remove the examples": the one just built, or one they run ("add a Take-home stage", "rename Candidate to Applicant", "add interviews to our Hiring space", "turn Status into a workflow") | `references/change.md`: read it, say in a few lines what will change, do it. Nothing of the team's is deleted, and a change that would lose or rewrite their data waits for a yes. "Remove the examples" deletes only the records whose names end with " (example)", then one line with how many went and stayed. |
| A question, not a request to build ("how should I model client onboarding in Fibery?", "what would a CRM look like for us?") | Answer in the conversation and build nothing. Read the design guide alone, and the workspace when Fibery MCP is connected (§2). Then give the model in a few lines, as the design guide's playback does: the things that become databases and what one record of each is, the stages, who does what, the view people open every morning, and what would link to databases they already have. No spec and no `design.md`. The last line offers to build it. On a yes, read the rest and go on from §3, asking only what the answer left open. |

The names they use become database, field and state names: a team runs a Space that speaks their language and abandons one that doesn't.

## 2. Read the workspace

Do this before asking anything: a Space that duplicates what the team already tracks is worse than no Space, and what the workspace leaves open goes into the same questions (§3). The design guide §2 says how to learn, reading only, what exists, what to **link** (the workspace's system of record for a noun: customers, employees, products), what to **create** (the nouns specific to this process), and which names are taken.

New database and field names are written the way the names nearest to them are: Title Case ("Date of Birth", short words lowercase in the middle), sentence case ("Date of birth") or lowercase. Only names people gave count: not Fibery's own fields (Name, Description, State, Creation Date, Created By and the like), not names Fibery made ("Meeting collection"), and not one-word names, which show no case. A field follows the other fields of its database (an existing one's, for a link's inverse or a people field's `user/<name>`); in a new database, or one whose fields show no case, the fields of the other databases in its Space; in a new Space, those of the workspace's other Spaces. A database name follows the other database names in its Space, and in a new Space those `get_spaces` lists. With nothing to go by, or a split between two cases, Title Case. Acronyms and proper names keep theirs, and the case of this skill's examples isn't the workspace's. Note the case in the Assumptions.

Language works the same way. You write to the person in the language they write in: the questions, the line while it builds, the report with its labels. The Space is in the language its team reads, which is the language of the names people gave in the workspace, or the person's when there is nothing to go by: every name, option and state, the descriptions, the guide with its title and headings, the sample records, and the texts the rules write. The English this skill shows is an example to translate ("How to run …", "Where to look", "My candidates"), with two exceptions kept as written in every Space, since they are how it is recognized later: the mark on sample records, " (example)", and the guide's last line, "Built by fibery-architect …". When the two differ (the person writes German, the workspace's names are English), the Space follows the workspace, even where the person's own words for things are in their language: it is one of the questions (§3), the Assumptions name it, and the report's first line says which language the Space is in.

## 3. Ask once

The questions are the only stop, except a change that would lose or rewrite the team's data (`references/change.md`). Ask at most four, the ones whose answers change what gets built and would be hard to change later: a database, a role, who uses Fibery, a second Space. What's easy to change after the build is never a question: names and words, an extra field and a select's options take defaults, written down in `design.md`. The workspace adds a question where it holds a real choice: an existing database that could be part of the solution, asked about by name ("Are your volunteers the people in Community/Member?"), the guess yes when it plainly serves the whole workspace or this team and no when it's only close; and a new Space's name that's taken (the guess: a new one beside it, "<name> 2"). The Space's language is a question too, when the person writes in another one than the workspace's names are in (the guess: the workspace's). Where the workspace has nothing that fits, the question about it isn't asked. An existing Space for the same process is a line, not a question: the new one is built beside it, and the line says that one could be extended instead. Notes on the sample data, on rules that might not build or on the app don't go with the questions.

Ask them all at once (an interview takes a few rounds, the last being its playback): each in their words, with your guess, and none about databases, views or rules. When your client has a tool for asking questions with choices (AskUserQuestion in Claude Code and Cowork), every round is one call to it. Each question gets a header of a word or two, 12 characters at most ("Trap bank"); your guess as the first option, with "(Recommended)" after its label; then one to three real alternatives. An option's description says in a few plain words what the person gets ("Trappers use their own traps"). The tool adds Other for a typed answer, so don't add one, and multiSelect is only for answers that add up (who uses Fibery). Closing the questions unanswered isn't a "go": don't build until they answer. Without such a tool, a round is one message, a numbered list the person can answer by number or with "go": each question, then your guess ("Do you lend out numbered traps? I'll assume yes."), with no table and no column of what each answer would change. Either way, one line says you'll build as soon as they answer, in about 5 minutes, a few more with an app: just before the call, or at the end of the message.

When the answers are in, or straight away after "just build it", write the design and build it in the same turn. Don't show the design or a summary, and don't ask whether to build, unless the person asked to see the design first. What you decide in their place (a default taken, a link made or left out, a name chosen) is written down in `design.md`, so it can be changed when they ask.

## 4. Write the design

Design and write it as `references/design-guide.md` prescribes: the spec in plain words, under a short list of what you assumed in the person's place. The standard is the **80% Space**, the one a team would have built for themselves after a month of running the process: enough to run it tomorrow, small enough to still feel like theirs. The design guide §3–4 give the rule for each part, from the number of databases to the custom app you consider every time; its numbers are ceilings for a typical process, never targets, so you decide what goes in, fewer is always fine, and what's left out is named in the guide's Make it yours. The person can ask for a starter Space or for everything; 80% is the default.

Save it as `design.md` in the working folder when you can write files; otherwise it lives in the conversation.

## 5. Build

Follow `references/build.md` in its order (a change, `references/change.md` §3): six `execute_code` scripts, each started from its template, and the guide's two direct calls, so a build is about ten tool calls, not a hundred. The structure comes first; then the formulas and the sample records together; then the views and reports, the rules and buttons and the empty app together, the rules made on since the records are in; last the guide, whose text mentions the views, with the checks of the sample story's promises. A helper writes the app's code only when the client can run one in the background, alongside the guide; otherwise you write it after the guide. A script runs once and logs what it made and what Fibery stored: after a failure, repair only what failed, with a direct call or the same script holding only what is missing; a `fixLogs` line that renames a Space or database stops the build. Don't delete anything to start over unless the person asks; then delete only the new Spaces.

A new build says one thing on the way. When script 1 has logged, write one line before you send scripts 2 and 4: the Space exists, linked with the address that log gives, and its views, examples and guide are arriving over the next minutes, so the person can open it and watch it fill. Nothing else until the report.

There is no separate verification pass: the scripts log the formula types and the stored rule texts, and check the sample data's promises, and the guide's last call opens the first view after the guide, once, to see the Space the way the person will; fix what looks wrong before the report. Never change a record to test an automation.

## 6. Report

A few lines for the person who will run the Space, each only when it has something to say (a change's: `references/change.md` §4):

> **TNR program is ready in Edge.** Start with the guide, [How to run the TNR program](…), which is one screen, then [In care](…) for the day-to-day.
>
> **Your turn:** set who can open the Space; share [Colony report](…) and [Volunteer signup](…) publicly (each form's Share button); add Description templates to Colony and Trapping.
>
> **Worth a look:** the Colony portrait tab on any colony: I couldn't open it, so I haven't seen it run.
>
> The examples are marked "(example)"; say "remove the examples" when you start for real.

- **Ready**, always: the Space ready in its workspace (several Spaces, each with its reason), then the guide and the first view after it, both linked; the only other links are the forms in Your turn. When the Space isn't in the person's language, this line says which one it is in.
- **Your turn**: what the person sets by hand so the Space works for the team, each with where in Fibery: who may open the Space; a form to share with people outside the workspace, linked; a number or date field's minimum and maximum ("0 to 100") and a date that should start as today ("Date: today by default"), since the build sets every other default the design gives; a formula's number format, when it came back decimal; a Description's template, the headings a new record starts with (the build names them in the database's description, and the hero record's Description uses them). Never the Space icon, and never a failure.
- **Not built**: a rule native actions couldn't do (`build.md` §5) or a part that failed, each with what's done by hand instead.
- **Worth a look**: what the build couldn't check itself, usually the app, with why in a few words.
- The last line says the sample records are marked "(example)", and that "remove the examples" deletes them when the team starts for real (§1).

Nothing else goes in: no counts, no list of views or of what the Space tracks, no assumptions, nothing about what reaches outside the Space, how the build was checked, its time or scripts, and no offers. All of it is in `design.md` for when the person asks: the Assumptions at its top, and **Build notes** at its end, written now, a line each: what was created (N databases, N fields, N formulas, N views, N reports, N automations, N documents, N apps, N sample records; the fields the build added, people fields and links in, a relation once, Name, Description, the state, comments and formulas out; the views without the documents); the scripts sent, fixes among them; each link with the field it added to its existing database, the field each people field added to every person, and any rule that writes to existing records; what was checked and what wasn't; the app considered when none was built; and any promise the sample data couldn't keep.

## Boundaries

- Never change, rename or delete anything that existed before the build, except when the person asks for a change to a Space (`references/change.md`); then nothing of the team's is deleted, and a change that would lose or rewrite their data waits for their yes. A new Space's build adds exactly three kinds of things outside it, all written down in `design.md`'s Build notes: the inverse field of each link on the existing database, the `user/<name>` field of each people field on the workspace's people, and a rule that writes to records of a linked database when the team's own records change, which exists only when the person asked for one, before the build or after it. The build itself never reads existing records into sample data, writes to them, or links sample records to them.
- The only records ever deleted are the sample data, when the person asks to remove the examples (§1): records the build made, found by their mark, never one without it.
- Parts of a Space the build made (a database, field, state, view or rule) are removed only on the person's word, and only while the Space holds nothing but its examples (`references/change.md`).
- Never put real people, customers, emails or record contents into sample data; sample data is invented, people are `me`.
- No migration from other tools in this version: neither their structure (a Notion or Airtable base, a Jira project, a spreadsheet) nor their records. If that's what the person has, say so, design from their process as they describe it, and point them to Fibery's import for the records afterwards.
- If the workspace already has a Space for this process, say so with the questions (after "just build it", in `design.md`'s Assumptions) and build alongside it (a new Space, links allowed), unless the person asks for that one to be extended.
