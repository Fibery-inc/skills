# Build guide

A build is six `execute_code` scripts, each started from its template in `scripts.md`, and the guide's two direct calls, with the app beside them. The spec you build from is `design.md`, or, for a recipe build, the recipe's Details for building with the delta in `design.md` applied on top: renames everywhere, links, additions, removals; whatever the delta doesn't mention is built as the recipe says.

Before the scripts · 1 Structure · 2 Formulas · 3 Views and reports · 4 Sample records · 5 Rules and buttons · 6 The guide and the last checks · 7 The app · 8 Shapes the templates don't show · 9 Troubleshooting. The scripts' templates are in `scripts.md`, under the same numbers.

## Before the scripts

`execute_code`'s own description says how a script runs. What it doesn't say: `get_fibery_skill` isn't there (call it directly), and the tools a script calls need no loading in the client (SKILL.md, What you need): their inputs are in the templates and in §8.

In this order, each message once the one before has answered:

1. **Script 1**, the structure and the guide's empty document: everything else hangs off them.
2. **Script 2**, the formulas, which read its fields.
3. **The rest, in one message:** scripts 3, 4 and 5, in that order, and the app script when there's an app (§7): views and reports, the sample records, rules and buttons, the empty app. None needs another, and script 5 makes its rules off, so none fires on the sample data.
4. **The guide's two calls and script 6** (§6): the guide mentions what the other scripts made, and script 6 checks the promises that read formulas, which Fibery has recomputed by now, then turns the rules on.

A script that logs "time is up" goes again, alone, before the next message. Fixes for scripts 3 to 5, and a view that filters on a sample record, go in a message of their own before the guide's, so the guide mentions what exists. The app's code comes after message 3: from a helper started in a message of its own as soon as message 3 has answered, when your Agent tool can run one in the background, or from you after the guide (§7). Then the report, once a helper is back. Only the app goes to a helper: a script takes seconds, less than a helper would spend reading its brief.

**Every script:**

- **Starts from its template** in `scripts.md`: replace the data block at the top with the spec's content, every name spelled as the spec spells it, and copy everything from `const fails` down unchanged. Write it straight into the `execute_code` call: `execute_code` reads no files, so a script assembled in a file first is typed twice. The data uses the tools' own input shapes; anything a template doesn't show goes into the same list in the tool's shape (§8), since the fixed part sends whatever the list holds.
- **Is one step:** calls that depend on each other follow in `await` order, calls that don't run together in `Promise.all`.
- **Stops in time, and says so.** One that runs about a minute is cut off with no logs ("connection lost", or "The upstream server is timing out"; measured: 55 seconds came back, 70 didn't), though Fibery usually finishes it. So every template but script 1, whose structure is one call, starts a call or a batch only while the time so far plus the slowest one yet ends by 45 seconds, counting at least 5 seconds for one, or 15 when Fibery's AI writes it (formulas, an automation's texts); that leaves about 15 seconds for the read-back and the logs. When it stops, it logs "time is up … run this script again, as it is, to finish": send it again at once, alone in its message, and it goes on from where it stopped.
- **Looks ids up by name when it runs, in this build's Spaces only:** states and options with `enumIds`, records with `byName`, views and reports with `query_views({space})`, you with `get_me`; never an id pasted from an earlier result, and never a name matched across the workspace: `get_reports_list` and `search` return every Space's views, deleted Spaces' reports included, and a fix script that matched a report by title wrote to another Space's report of the same name.
- **Does only what's missing, and logs what it found:** it reads what exists first, and its log names what was there before as well as what it made ("made: nothing; there before: Spaces 1, databases 5, fields 31, workflows 5, apps 1"). So a script that failed, stopped or was cut off runs again as it is and its log then says the step is complete, and a build interrupted anywhere (a client timeout, a new conversation) resumes by running the scripts again from 1, half a minute after the last one, since a script can finish after its result is lost. `create_schema` skips what exists, so a fix that adds a field or a database sends it only what's new; the per-kind schema calls are atomic instead: one field that exists fails its whole batch.
- **Logs little:** one line per failure, counts for the rest, the checks' findings, `failed 0` when the step is done. The tool's result also lists an artefact per write; read the logs.
- **Is fixed by a script:** one short script in the next message fixes every failure, each call at most twice; then skip what depends on it and report it. A fix script copies the template helpers it needs: `run`; `rows`, a query's rows; `byName`, a database's records by name; `enumIds`, states (`workflow/state_<Space>/<Database>`) or options (`<Space>/<Field>_<Space>/<Database>`) by name; `day(-3)`, three days ago.
- **Stops on someone else's Space:** a `fixLogs` line that renames a Space or database means the call went somewhere else, and script 1 stops when a Space of the design's name holds databases the design doesn't have (§9).

## 1. Structure

One script: it numbers any inverse name that's taken, makes every Space, database and field in one `create_schema` call, a second or two, then the guide's document. `create_schema` skips whatever exists and checks the whole spec before it changes anything, so a spec it refuses has made nothing (§9). Its data is the call's input, in the spec's words, each field by its short name and in the spec's order:

| The spec says | In the data |
|---|---|
| a Space | `spaces`, by name: its `color` and `description` (Colors, below) |
| a database | `databases`, keyed `"<Space>/<Database>"`: its `color`, `description` and `fields`, and `comments: true`, `icon: true` or `avatars: true` where the spec has them. Name and Description come with every database: leave them out of `fields` |
| text, number, checkbox, place, date | the type's name: `text`, `email`, `url`, `phone`, `int`, `decimal` (`{type: "decimal", meta: {"ui/number-precision": 1}}` for its places), `checkbox`, `location`, `date`, `date-time`, `date-range` (`date-time-range` when the hours matter) |
| a number's unit | `{type: "int", meta: {"ui/number-unit": "h"}}`, or `decimal`, only where the number alone is ambiguous: a time, length, weight or size people measure in more than one unit (an Estimate in h or d, a Distance in km or mi). None where the name or the process settles it, as for most numbers: a score or a scale, a count of things, an age, money or percent. Fibery shows the unit as written after every value and never pluralizes it, so it is the short form: h, min, d, wk, km, mi, kg, GB. A formula's unit follows the same rule, written with its result in the spec ("a whole number, h"), and none when its name says it (Days in stage, Km last 30 days); `create_formula_field` can't set one yet, so until it can the build leaves it out |
| money | `money`, in USD, or `{type: "money", meta: {"ui/number-currency-code": "EUR"}}`: the currency of the workspace's money fields, or the one the person names, or USD, an assumption `design.md` names |
| percent, as a field | `percent`, holding a fraction (0.25 shows as 25%); a percent formula is a whole number from 0 to 100 (§2), so a threshold written for one never serves the other |
| single select; multi select | `{select: [...], default}`, the options in order and the default's name; `{multiSelect: [...]}`; each option `{name, color, icon}`, the `icon` unless the select is an exception below |
| states | `workflow`, never a select: the states in order, each `{name, type, color}`; the first state and any marked "(not started)" are Not started, "(finished)" ones Finished, the rest Started. The first is the default, unless another has `default: true` |
| relation | `{relation, back, cardinality}`, declared once, on the side the spec names: the other database, the inverse's name, and the cardinality from this side (`many-to-one`: many of these to one of those) |
| person; people | a relation to `fibery/user`: many-to-many for a role a "My …" view filters on, even when one person holds it, since "contains me" works on a to-many people field only; many-to-one otherwise. Its inverse lands on every person in the workspace, so the script numbers a taken name ("Recruiting 2") and logs it, and the Build notes name it |
| link to an existing database | a relation on the new database, the target exactly as `schema` shows it; a taken inverse is numbered and logged the same way |
| files | `file`, or `files` for several; a gallery's cover is one of them (§8) |
| rich text | `document`; `NO_DESCRIPTION` deletes the Description where the spec says "no description" |
| a field's description | `description` beside its `type`, or beside a relation's keys, only as Descriptions, below, says |
| the guide | `GUIDE`, the document How to run <process>, in the main Space: script 1 makes it before any other view, since a Space lists its views in the order they were made, so the guide always comes first; §6 writes its text |

**Colors.** Every database gets the palette color its name brings to mind, the one a person would pick for it: a Cat light gray, a Clinic day bright red, an Invoice green, a Night shift deep purple. The main database picks first, then the rest in the spec's order. No two databases share a color: when the one a name suggests is taken, or is a near twin of one taken (Orange, Red-orange and Brown-orange; Green and Yellow-green; Sky blue and Cyan; Deep purple and Blue-purple; the three greys), take the next best fit, and a name that suggests nothing takes a free color far from the others, never a grey. Each Space takes the color of the first database the spec puts in it, so the main Space wears its main database's color. The palette: Dark gray #4A4A4A, Blue-gray #6A849B, Light gray #99A2AB, Bright red #D40915, Pink #E72065, Magenta purple #9C2BAF, Deep purple #673DB6, Blue-purple #3E53B4, Bright blue #2978FB, Sky blue #199EE3, Cyan #1FBED3, Teal #159789, Green #4FAF54, Yellow-green #8EC351, Orange #FBA32F, Red-orange #FC551F, Brown-orange #B04E31. The icon can't be set, and the report leaves it out. A Space's description ends "Built by fibery-architect from <the recipe's title, or the design's name>, <date>.", so it can be recognized later.

**Option emojis.** Every select gets an emoji on every option, the one a person would pick: priorities (High `:fire:`, Low `:snowflake:`), health (`:large_green_circle:`, `:large_yellow_circle:`, `:red_circle:`), channels (`:email:`, `:telephone_receiver:`, `:speech_balloon:`), kinds and sizes. The exceptions are options that are names (clinics, places, people, products, departments, countries), where any emoji would be arbitrary, and lists longer than about eight; states can't take one. The `icon` is a shortcode with colons, as Slack names emojis: an unknown one, a raw emoji or an empty string isn't rejected but stored as a random emoji (measured), so script 1 reads the icons back and logs every one stored differently. An alias is fine (`:thumbsup:` comes back `:+1:`); for any other, send `update_single_select_fields` or `update_multi_select_fields` with `update: {updateOptions: [{name, icon}]}` and another shortcode.

**Descriptions.** A field gets a description only when its name leaves a question: a scale or a period ("1 to 5, 5 a strong hire", "per year"), never a unit the field shows, what counts ("how many people this role hires"), or that a rule fills it ("Set by Stage changed when the state changes"). Email, Phone, Resume, Recruiter, Job or Due date need none: leave `description` out. Select and workflow fields can't take one, so their guidance lives in the option names and the database's description; a formula's description is the prompt Fibery writes it from (§2), and Fibery MCP has no way to set another.

The template is `scripts.md` §1.

## 2. Formulas

One script, `LEVELS` in dependency order: the formulas that use no other formula, then the ones that use those, and so on, as many levels as there are. It sends four at a time and stops in time, and a rerun goes on from where it stopped. The rest waits until it logs no "time is up".

`create_formula_field` takes no code: Fibery writes the formula from the description, in about 11 seconds. The description is the spec's meaning in one sentence, naming every field exactly and saying the result type ("The result is a whole number" / "a decimal with one decimal place" / "text" / "true or false" / "a date" / "a date range"); when the spec gives an expression, the formula has three or more conditions, its result is money, or it divides, averages or counts a share, it adds "Use exactly this Fibery formula: <expression>", and then the description can be just that and the type sentence, however long the expression (descriptions of 398 and 408 characters were accepted, measured): left to itself, Fibery's writer wraps a share in `Round` (which makes it decimal), can type a money result as a whole number, and adds clauses of its own. Fibery's syntax, as it writes it: fields in brackets (`[Stage changed on]`), or bare when one word; `If(c, a, b)`, `IsEmpty(x)`, `and`, `or`, `=`, `!=`; `State.Name = "Done"`; `Today()` and `ToDays(date - date)`; a collection's `Filter(…)`, `Count()`, `Avg(Field)`; `Greatest(a, b)`, `Round(x, places)`; a range's `Dates.Start()` and `Dates.End()`.

The type is fixed when the field is created, and `update_formula_field` keeps it:

- An average of whole numbers is typed whole, `If([Parts].Count() = 0, 0, [Parts].Avg([Score]))`, and needs no `Round`: `Round` or `Least(100.0, …)` over a whole number is rejected ("Expected argument of type 'Decimal' but 'Integer' found"), and multiplying by 1.0 makes it a decimal (measured).
- Division, `ToDays` and `Round` (which Fibery sometimes adds itself) give decimals, and a decimal shows two places (6.00), a format nothing in Fibery MCP sets. But an `If` takes the type of its first branch, so a whole number stays whole when its formula starts with the case that gives 0, and Fibery rounds the other branch (measured): `If(IsEmpty([Stage changed on]), 0, ToDays(Today() - [Stage changed on]))` is typed integer; the same with the branches swapped, with a date-part fallback, or with a `Round` in the other branch is decimal, while `Greatest` and `Least` over whole numbers stay whole. The rule also works the other way: a decimal or money result with a 0 case writes it `0.0`, since `If(IsEmpty([Amount]), 0, [Amount] * [Probability] / 100)` is typed integer even over a money field, and the same with `0.0` decimal (measured). A day count therefore reads one date field, and the rule that stamps the date also fires on `created` (§5). When no 0-first form fits, accept the decimal, since thresholds work on it the same, and put its number format on the report's Your turn; for a recipe that said a whole number, it is also a Change row.
- A percent is a whole number from 0 to 100, its 0 case first ("the share of runs won, as a whole number from 0 to 100, 0 with no runs"), never a fraction, which people would see as 0.5714…; every threshold on it is on that scale. It multiplies by 100 once: Fibery's writer has multiplied a share by 100 both inside and outside the division, so check the expression.
- A date range is stored with an exclusive end, but in a formula `Dates.End()` is already its last day (measured): days left are `If(IsEmpty(Dates), 0, ToDays(Dates.End() - Today()))`, typed integer; say "the last day of Dates, Dates.End()". A day count from a date-time says "the date part of Creation Date", or a record created today counts -1. Formula fields have no `Now()`: Fibery writes `Today()` instead (measured), so a date-time compared in a formula ("Promised by has passed") turns true only when the day turns; a red card at the exact moment is a view filter in minutes (§8). A date computed from a date-time (Creation Date plus three days) comes back a date-time.
- Fibery can't write an empty branch: an `If` that should be blank in one case gets a value there (0, a far-future date) that the view filters out.

The template is `scripts.md` §2.

The log shows each formula's type and expression. Compare both with the spec before the next message: the type, and every condition, comparison and fallback, since Fibery's writer can drop a clause or add one and keep the type. A wrong type: delete and recreate in the next script, while nothing uses the field yet. A wrong expression: `update_formula_field({database, name, description})`, the field's full name in `name` and "Use exactly this Fibery formula: <expression>" as the description.

A report that keeps only some linked records (only key results whose objective is Active, only runs of strats that aren't Retired) needs a true-or-false formula on its source ("Objective active"), since a report filters on its source's own fields: the design lists it with the formulas (in a recipe's delta, as a Change row), and it is created here with the others.

## 3. Views and reports

Every view, document and report in one script: the state and option ids looked up first, the views created six at a time, then the reports, and every nested view read back for one root. It stops in time like the others, and a run creates what's missing, adds the tabs a report lacks and removes a leftover default tab, so a rerun also repairs a report whose chart was rejected. Each view gets its type, name and config, its Space (its database's, or the one the spec names after the view's name, "Owner contacts, in Dog owners"; documents in the main Space, the guide already made by script 1), and a `description`: the question it answers, in one line, the design's Answers or what the recipe's What people look at says it's for.

- Every grid gets `rowHeight: "short"`, and every grid's and list's items start their `fields` with the Name: Fibery appends a missing Name as the last column. After the Name, the spec's Shows go in the order a person reads a row, whatever order the spec lists them in, on cards too: what the record is part of (its parent, Job on a Candidate); where it stands (the state and what measures it: Days in stage, Health, a flag like Is stuck); who (the people fields, together); what kind (the selects); when (dates in the order they happen, a range's start before its end); how much (numbers and money); then contact details together, other links and text. A field sits with what it's about, whatever its type: a formula right after the field it reads (Openings, Hired count, Openings left; Deadline, Days to deadline), a pair side by side (Salary min, Salary max). Nested items are ordered the same way, each on its own.
- A view shows its database's own fields only: a linked record's field (the customer's Phone on a repair) is a formula on the database (`[Customer].Phone`), made in script 2. `create_view` takes a path such as `{field: ["Shop/Customer", "Shop/Phone"]}` without an error and stores nothing for it.
- A calendar gets no card fields, whatever the spec's Shows says: each one squeezes the name down to its first letter, so the color carries the kind or state. A timeline bar takes one short field at most. Both use one field for start and end, a date range or a plain date or date-time, unless the spec names two.
- Children nest through a to-many relation only, one item per level and each database once; a database nests inside itself through one item pointing at its own index (§8). A view that asks to nest through a to-one is dropped and reported.
- A board or timeline groups by a state, select, relation or people, never a number, text or date: if the spec says otherwise, the spec is wrong, not the call.
- Cards that show a picture make a gallery, even where the spec says board: a Fibery board has no cover, and `create_view` drops one without an error. The board's columns become the gallery's lanes (§8).
- A view that filters on a specific sample record waits for the records: a short script creates it after script 4, before the guide.
- A document view is created empty, with its `space`; §6 writes its text.
- A report is one per database and mode, its charts its tabs in the spec's order: two charts on the same database are never two reports, which would each store and refresh the same records. A tab is a chart, or a metric for a single number, never a table. The script creates the report, adds the tabs it lacks one at a time (one added on a rerun comes last) and then removes the empty default tab, titled "Chart", which can't be given dimensions afterwards; while no tab of the spec's is there the default tab stays, since a report's last tab can't be removed. The records every chart keeps are the report's `filter`, sent as the source's `filterPrompt`: one sentence naming the fields exactly ("only candidates that have a Job"), which Fibery turns into a query filter on the source, so the report stores only those records. The log shows the filter Fibery stored: compare it with the spec, as the formulas, and send a wrong one again, sharper, with `update_report({reportId, sources: [{database, filterPrompt}]})`, which keeps the tabs. A relative date stays out of it: "created this year" was stored as 2026-01-01 for good. Dates and what one chart keeps are its tab's `fieldConditions` (their operators are in §8). Report fields are named without their Space (`[Publish date]`), the state is `State`, a relation its title, the id `Id`; a true-or-false field and a relation are text there (`{field: "Strat retired", operator: "is in", value: ["false"]}`), and only the source's own fields are there: a condition on a linked record's field needs the formula from §2. A historical report (time in state, change over time) is `mode: "historical"` in `REPORTS`, its chart's conditions starting with `{field: "Modification Date", operator: "range", value: "LAST 90 DAYS"}`; there a field that isn't part of the history is named "<Field> (current value)" (`{field: "Objective active (current value)", operator: "is in", value: ["true"]}`), as `display_report_schema({databases, sourceMode: "historical"})` lists. `display_report_schema({databases: [...], sourceMode})` only when a chart is rejected.

The template is `scripts.md` §3.

The script ends by logging the url and the mention of every view, document and report, and each document's secret with, when it's empty, its one empty block, for §6. `VIEWS` is a function because its filters need the ids the script looks up first, and so is anything shared that is built from them (`const LATE = () => days("Due", "is-before", 0, true)`): a constant built at the top fails with "Cannot access 'flag' before initialization". `STATES` lists the databases whose states it uses, `OPTIONS` the selects. The builders (`fld`, `wf`, `sel`, `and`, `or`, `flag`, `num`, `empty`, `mine`, `days`, `stateAxis`, `byState`) are one line each in the template; `days` counts in days unless its fifth argument names another unit (`days("Next update due", "is-before", 0, true, "minute")`, before now). Every matching color rule applies, so the rules after a red one carry its opposite, as Pipeline's amber rule does; `byState`'s third argument adds that condition to every state's rule (`byState(C, {Applied: "#99A2AB", Offer: "#FBA32F"}, flag("Stuck", false))` after the red Stuck rule).

## 4. Sample records

The records are the script's data, written from the spec's sample story and database sections: what a team a month in would have.

- **How many:** 25–40 in all, 8–15 on the main database and a few on each supporting one. A recipe's sample story names no counts: give each database what the story's moments need, past 15 on the main database when they need it (four campaigns with their posts, plus loose ideas, came to 22 posts), and keep the total inside 25–40; past 40 only when the story's moments and promises need it (a check in behind every Last check in came to 44), never past 50.
- **The story's moments exactly as told:** the hero where it stands, the late one, the stuck one; around them, records in every state, and two or more in every board column that matters.
- **Names** as the team would write them, or by the story's naming rule, and unique within a database, since the script finds records by name ("Laptop for Ana", "Laptop for Ben"); the script adds " (example)". Companies that don't exist, emails at example.com.
- **Dates** in days from the build day, spread over the past quarter and the next month; a story's "Tuesday" or "last week" is an offset too, never a calendar date.
- **Links** by the linked record's name; **people** as `"me"`.
- **One hero per main database**, with its Description in Markdown showing how the team writes one.
- **Every field a role fills every time**, filled, and every field a rule keeps (a date stamped on a state change), filled from the story, since the rules stay off until the records are in (§5).
- **The promises kept:** every record satisfies What must stay true as if the rules had run. A shipped pitch has every scope Done; a key result with a Last check in has the check in behind it; an official match calls only Match ready strats. A Space that contradicts its own promises on day one teaches the wrong habit. The exception is a record the story shows breaking a promise on purpose, the red card a flag exists for: its check leaves it out by name.
- **Only dates the build can set.** Records are created at build time, and Creation Date can't be set ("Cannot update "fibery/creation-date" readonly fields"): a moment that needs an older record (an update posted ninety minutes ago, a postmortem past a due date counted from its creation) shows only through a date field the record has, and otherwise goes under For the recipe in `design.md`'s Build notes.

Invent freely around the story, but never a real person, company or record of the workspace, and never a link to an existing database's records.

`CHECKS` hold one line per promise on stored values, or per Must hold cell, each a query's `select` and a `bad` test that finds the records breaking it (pitches in *Bet* with no appetite; *Shipped* pitches with a scope not *Done*). Decimal values come back from `query` as strings ("25"), so a check compares `Number(r.x)`. A promise on a collection selects it as a sub-query whose `q/from` is the field's full name as a string, `skills: {"q/from": f("Skills"), "q/select": {n: "enum/name"}, "q/limit": "q/no-limit"}`, people and multi selects included; a path through a collection, or a `q/from` list, is rejected. A promise kept in comments selects them the same way, `cs: {"q/from": "comments/comments", "q/select": {id: "fibery/id"}, "q/limit": 1}`, with `bad: r => … && !r.cs.length`. A rich text is read with `read_document`, since its Snippet lags behind an insert. A check that reads a formula goes in script 6, at the end, since Fibery recomputes formulas a few seconds after the writes. Fix the data in the next script until every check holds; a promise no query can see (a practice, an app's behaviour) is reported as not checked.

The template is `scripts.md` §4.

A record's keys are field names without the Space; the script reads each field's type and converts:

| Key | Value |
|---|---|
| `Name` | the name; the script adds `X` (" (example)") |
| `state` | the state's name |
| a to-one relation | the linked record's Name |
| a to-many relation | a list of Names |
| a person, people | `"me"`, `["me"]` |
| a single select | the option's name |
| a multi select | a list of option names |
| a date | days from today (`-3`), or `"YYYY-MM-DD"` |
| a date-time | `[days, "HH:MM"]`, UTC |
| a date range | `[first day, last day]` in days from today; the script stores the exclusive end |
| a rich text field (Description) | Markdown |
| `comments` | a list of comments in Markdown |
| a date inside a text or comment | `${day(-2)}` in a template string, since `day` is defined above the data |
| a gallery's cover (files) | `[cover("Rack focus", "#2978FB")]`: the record's name and its lane's color |
| a location | an object, never a string: `{latitude, longitude, fullAddress, addressParts}`. `addressParts` is never left out, or the create is rejected: the parts you know (`address` for the street, `place` for the city, `country`), or `{}`. Fibery doesn't look an address up, so the coordinates are the pin: put sample places in one real city, near its centre, with no invented house numbers |
| anything else | the value as Fibery takes it: a number, text, true or false, a percent field as a fraction |

Databases may come in any order: to-one links are set once every record exists. Every run fills what each record of the data still lacks, new or already there: an empty to-one link or person, a state that isn't the story's yet, collection items not yet linked, an empty rich text, comments on a record that has none. So script 4 runs again as it is, like the others, after a cut-off, a "time is up" or a fix to its data, and never doubles a comment or a text; a value already set is changed by a short script of its own (`update_entities`, or `delete_entities({database, ids})` for records). A file field stays empty, since a sample file would have to be a real one, uploaded from the computer or fetched from the web; leave its key out, and the Build notes say so. A gallery's cover is the exception, so the gallery opens with pictures: every record on it gets a placeholder, `cover(name, color)`, a block in its lane's color (its state's or option's, else its database's) with its name on it, which Fibery downloads from placehold.co; a record that has a picture gets no other.

## 5. Rules and buttons

One script, in the message with scripts 3 and 4. It creates four at a time and stops in time, and turns each new rule off as soon as it exists, so none fires on the sample data written beside it; script 6 turns them on (§6). A schedule starts the day after the build, at the spec's time, in UTC, and the guide says "UTC" next to the time. A rule that stamps the date a day count reads (Stage changed on) gets `created` as a second trigger, so every new record has it and the count stays a whole number (§2); a rule filtered on states no record is created in doesn't need it.

- **Native actions only.** A rule or button never uses the `Script` action, whatever the spec says; `execute_code` builds the Space and never becomes part of it. Its condition is the filter, its texts are templates, and a rule with two conditions becomes two rules. An action no native shape can do (a comment on a linked record, a notification to the people of linked records, a check before acting, a value found by searching other records, email), or one rejected with no native shape in §8, is left out: the rule is built with the rest when the rest still does its job (Actions done still moves the postmortem to Closed, without its comment), and not at all when that action is its point (All parts in exists only to tell the builder). Either way the report lists what wasn't built and the guide names the step as done by hand. A rejected action fails its whole rule, so send the rule again without it.
- **Buttons take no filter and can't check:** a button acts whatever the record's state, so its description and the guide say when to press it.
- **Texts and formula values are prompts**, and Fibery writes the result (10–20 s each): "a short note naming who clicked the button and the publish date", never the finished text. A prompt names the literal words a text must contain: "The words 'Interview today:' followed by the interview's Name" came back as `Interview today: {{Name}}`, where "The interview's Name is today" came back as a bare date. A value carried from the record that triggered the rule names that record, and the target's field of the same name when there is one: "the Health of the Check in that triggered this rule, not the Key Result's own Health" (without it, Fibery took the target's: `[Step 1 Check in].[Key Result].Health`). A date-time stamp says "the current date and time, using Now(), not Today()": other wordings stored midnight (`DateTime(Year(Today()), …, 0, 0, 0)`) or `Today()`, and even this one is read back (measured).
- **Read back what Fibery stored:** the script logs each automation's triggers, stored filter and actions; read the filter and every text and formula value against the spec. Resend once, in the next script, with `update_automation({automationType, id, changeActions: [{actionId, action, args}]})` (the ids from `query_automations`; `triggers` and `filter` replace the stored ones the same way) and a sharper prompt when one names a field the database doesn't have, multiplies a 0–100 value by 100 ("followed by a percent sign, never multiplied"), picks the wrong record ("the last item" for the one just added), or points at a field off the path; still wrong, drop the action, or the rule when the action is its point, and list it under Not built.
- **An `updated` trigger names its fields** (`updatedField: ["workflow/state"]`); without them the rule fires on every edit of the record.
- **Existing databases:** a filter through a link to one is fine (read its `schema_detailed` for exact names); an action that writes to its records reaches outside the Space, so it exists only when the person asked for it, and the Build notes name it.
- `display_automations_schema` only when an action is rejected by name: its catalog runs to about 17K characters, mostly integrations.

The template is `scripts.md` §5.

The builders: `wf`, `and`, `or`, `flag`, `num`, `empty` and `days` as in §3; `stateValue` sets a state; `tpl` a text and `formula` a value Fibery writes from a prompt; `tomorrowAt(8)` a schedule's first run. Other triggers, actions and values: §8.

## 6. The guide and the last checks

Written last, since its text mentions what the other scripts made: two direct calls, in one message with script 6, which holds the checks that read formulas (§4), recomputed by now, and then turns on the rules script 5 left off, in the databases `RULES` lists. Script 6's template is `scripts.md` §6; fix what it finds broken in the next script.

**Its text.** The guide the design guide describes under Documents, one screen and under 500 words, for a recipe build too: the recipe teaches the method, the guide teaches this Space. From a recipe, write it with the delta applied (every rename, removal and Making it yours bullet taken, so nothing the guide names is missing) and the workspace's specifics where the recipe left a choice. Its parts come from the recipe's: the promise; How it runs, cut to its bold moments in order, each a line that says who acts and in which view; What people look at, as Where to look; the ★ promises of What must stay true; and up to three requests for the parts Making it yours says the recipe leaves out on purpose. A rule that wasn't built is named in its step as done by hand. The last line, in italics, links the recipe for the whole story: "The whole story, with the why behind each step: [Shape Up](https://github.com/Fibery-inc/process-cookbook/blob/main/recipes/software/shape-up.md)". A cookbook recipe links its page, `https://github.com/Fibery-inc/process-cookbook/blob/main/` followed by its `path` in the index (`recipes/<domain>/<id>.md`); a recipe from a link links that link; one attached or pasted gets no last line.

**Its mentions.** Every view, form, report, document and app named in Where to look, which leaves the guide itself out, is a mention there. Elsewhere a view is a mention where it first appears in each section. A layout app has no view of its own: name it as a tab on every record of its database. Rules, buttons, databases, fields, states and records stay plain names, so the guide reads as a story whose doors are the views. A view that failed is named without a mention, and the guide says so.

**The calls.** Put each mention in the text exactly as script 3's log gives it, or the app script's for a page app, where the view's name would go: "Every morning, open [[Pipeline#^a0b03b18-8310-4435-992e-da09b5f17bcd/59043a92-3e58-4dac-8081-084c171cd3c8]]." The whole string, both ids included: a shortened one, such as `[[Pipeline]]`, stays plain text. Never write one by hand or put a url in its place; the recipe in the last line is the guide's one link. Then `replace_document_blocks` (no Fibery skill to load first; its result echoes every block, so read only that it succeeded) with the document's secret and empty block from the same log and the whole text in one replacement, `{secret, blocks: [{blockId: <block>, content: <text>}]}`, sent only when that log says the document is empty, so a resumed build never writes it twice. The second call is `fetch_view_data` for the first view made after the guide, its `publicId` the last part of its url, with `limit: 5`. Read those cards as the person will see them and fix what looks wrong before the report; a view with nested items comes back as one flat list per database, children unfiltered by their parents, so read its root items. Any other document in the spec is written the same way.

## 7. The app

The spec describes the app and never contains its code: the code is written now, from the spec's "how it works" and the built Space's real names and ids, so it matches both and today's app platform. `get_fibery_skill({skill: "custom-apps-dev"})`, a direct call, never in a script, is the source of truth for the stack, the `@/lib/fibery` API, theming, the files you may change, the token (`create_custom_app_dev_token({appId})`, from a one-line script or directly) and the download and upload requests; the three rules below are this build's own and stand. The download and upload need the web, which `execute_code` has no access to: this runs in Bash.

The app script, `scripts.md` §7, comes first: `APPS`, `{name, kind: "view", spaceName}` for a page in the Space (without `spaceName` it lands in the private space) or `{name, kind: "layout", databaseName}` for a tab on every record page, and `APP_TOUCHES`, the databases (`C`) and fields (`[C, f("Days in stage")]`, `[C, "workflow/state"]`) its code uses. It makes the empty app and logs its id, a page app's url and mention, and those ids, on every run.

You run the app script, in the message with scripts 3 to 5, so the guide can mention a page app. When your Agent tool can run a helper in the background (an option such as `run_in_background`), a helper of your own model then writes the app with this brief, started in a message of its own as soon as the app script has logged, while you go on to the guide. Otherwise you write it yourself after the guide: a helper call that waits for the helper holds up everything sent after it (measured in Cowork: a script sent beside a 30-second helper ran only when the helper was done), and only adds its hand-off.

```
You are writing the custom app "<name>" for the new Fibery Space "<Space>". Read <path to this file> §7
and load Fibery's custom-apps-dev guide with get_fibery_skill. The app is made and empty; its script
logged: <the "app" and "ids for the app" lines>. The app: <kind and purpose, and "how it works" from the
spec>. Writes: <the only fields it may change>. Names: <the full name of every database and field it
touches>. Upload description: "Built by fibery-architect from the design <name>". Change nothing else in
the workspace. Reply when the upload has built, or after three failed builds with the last error.
```

1. **Write the app**, usually only `src/App.tsx`, by three rules:
   - Build exactly what "how it works" describes: what it shows, what people can click, drag or type, what it changes and when it saves, what it shows with no data. No features beyond it.
   - Look names up when the app runs, by id, because people rename things: `getSchema()` once, then `schema.getTypeObjectById(<database id>)` and `typeObject.getFieldObjectById(<field id>)` give the current names; the title field is the type's title field, the workflow field is always `workflow/state`, and a field without an id is found by its title within its database. The names are the fallback when a lookup finds nothing, and a clear message the fallback for that.
   - Change only the fields in Writes, and add no packages.
2. **Upload** as the guide says, with the app id and the token set in the same command as the request: a shell call doesn't keep the variables of the one before, and an upload without them answers "Unauthorized". If the result is `failed`, read the build output, fix the code and upload again, up to three times; then report the last error.

Without web access to the workspace, the app stays created but empty: report it as "created, not built", and give the person the "how it works" brief to paste into the app's AI builder in Fibery.

## 8. Shapes the templates don't show

**Views**, `create_view {viewType, name, space, description, config}`:

- An item is `{database, fields, filter, orderBy, colorCoding}`. A field is `{field: "Space/Field"}`, the state `{field: "workflow/state"}`, a collection shown as a count adds `showCount: true`; a sort is `{field, direction}`, with `dateRangeSortBy: "start"` or `"end"` on a range.
- **list**: a grid without `rowHeight`. **board**: `x` and `y` axes, one entry per items database, each `{forDatabase, field, database, fields: []}` naming a lookup database, `workflow/state_<Space>/<Db>` for states, `<Space>/<Field>_<Space>/<Db>` for a select, the target database for a relation or link, `fibery/user` for people; `y` may be `[]`. A timeline's lanes are `y` axes the same way.
- **Nesting:** a child item has `groupBy: {parentIndex, parentField}`, the parent's to-many field that targets the child. A database nests inside itself with one item pointing at its own index through its own to-many field: `{"database": "OKRs/Objective", "groupBy": {"parentIndex": 0, "parentField": "OKRs/Supported by"}}`, with Key Result's item under index 0. Listing the database twice builds two roots, not a tree. A child item's filter hides children only: filter the parent item too when only parents with such children should show.
- **form**: any field may be on it, people, multi selects and the Description included, each with `required: true` when the spec marks it. Defaults: a string, number, boolean or ISO date; `{id}` for a select, state or to-one; `[{id}]` for a to-many; `hidden: true` keeps a defaulted field off the form. Nothing makes a form public: sharing it goes on Your turn.
- **map**: each item adds `location: f("Location")`, its location field.
- **gallery**: each item adds `cover: f("Frames")`, a files field (a gallery without one is rejected), and `fillCover: true`; lanes are `y` axes as on a board, each with `hideEmptyLanes: true`, so a lane without cards (No Craft among them) takes no room; `cardSize: "medium"`, or `"compact"` for many records. Feed, gantt, embed and canvas views: `get_fibery_skill({skill: "views"})`.

**Filter nodes**, `{nodeType, args: {fieldPath, operator, value}}`, without `value` for `is-empty` and `contains-me`:

| nodeType | fieldPath and operators | value |
|---|---|---|
| `workflow` | `["workflow/state"]`; `is-any-of`, `is-none-of` | a list of state ids |
| `single-select` | `is-any-of`, `is-none-of`, `is-empty` | a list of option ids, even for one |
| `reference` (to-one) | `is`, `is-not`, `is-empty`, `is-not-empty` | a record id |
| `collection` (to-many) | `is-empty`, `is-not-empty`, `contains-any-of`; `contains-me` on a to-many people field only | record ids |
| `number` | `greater-than-or-equal`, `less-than`, `equals`, `is-empty` | a number |
| `bool` | `is` | true or false |
| `text` | `is-empty`, `contains` | a string |
| `date` | `is`, `is-before`, `is-after`, `is-on-or-before`, `is-on-or-after`, `is-empty` | `"YYYY-MM-DD"`, or `{amount, unit, isBeforeNow}` with all three keys, `unit` one of `minute`, `hour`, `day`, `week` |

Relative dates: "is today" is `is` with `{amount: 0, unit: "day", isBeforeNow: false}`; "before today" is `is-before` with `{0, "day", true}`, the start of today, on date-times too; "in the next 7 days" is `is-on-or-after` `{0, "day", false}` and `is-on-or-before` `{7, "day", false}`; "more than 14 days ago" is `is-before` `{14, "day", true}`; on a date-time, "before now" is `is-before` `{0, "minute", true}`, since days count from the start of today. A to-one person field has no "me": a "My …" view needs a people field. A range's start or end is `["q/start", "Space/Dates"]` or `["q/end", …]`, the end being the stored one, a day after the last; a linked record's field chains, `["Space/Pitch", "workflow/state"]`; `{nodeType: "logical", args: {operator: "and" | "or", filters: [...]}}` nests.

**Rules and buttons**:

- **Triggers** besides `created`, `updated` and a daily schedule: `{trigger: "collection-item-added", args: {changedCollectionField: "Space/Seen in"}}` (`collection-item-removed` likewise), either one the rule's only trigger; a weekly schedule, `settings: {unit: "week", time: {hour: 9, minute: 0}, daysOfWeek: ["monday"]}`.
- **Actions**, by name: "Update" this record; "Create" a record of the same database (a weekly review on a schedule), its `fields` the new record's; "Update <Relation>" its linked records, with a `filter` on them when the relation is to-many, a filter node on the linked database's fields (`{action: "Update For repairs", args: {filter: wf(R, "is-any-of", ["Waiting for parts"]), fields: [{name: "workflow/state", value: stateValue(R, "Queued")}]}}`, with `R` in `STATES`; a to-one takes only `fields`: put the condition in the rule's own filter, chained through the relation); "Add <Relation> Item" creates a record linked through a to-many, "Add <Relation>" through a to-one, their `fields` the linked database's; "Unlink <Relation>"; "Add comment", on this record only; "Notify <People field>" with `subject` and `message`, or "Notify Users" with `to: {type: "formula", prompt: "the creator"}`, never with a formula through linked records' people, which is rejected ("Ouch, we can't calculate…") and fails the whole rule; "Append content to <field>"; "Send Web Request". State and select values go by id.
- **Values:** `{type: "value", value}` with a literal, `{"fibery/id"}` for a state, option or record, or a list of those; `{type: "formula", prompt}`, also for a value carried from a linked record ("the Next cycle of this pitch's Betting table"); `{type: "template", prompt}`; `{type: "empty"}`; `{type: "user-provided-value"}` on a button. Prompts are plain words naming fields exactly, never code or formula syntax.

**Reports:** `add_chart_tab {reportId, title, type: "stacked-bar" | "bar" | "line", x, y, color, fieldConditions, palette}`; a horizontal bar puts the count on `x` and the category on `y`. A single number is a metric tab, `{title, metrics: [{expression: "COUNT([Id])"}]}` in the report's `tabs`, which the template adds with `add_metric_tab`. Expressions: `COUNT([Id])`, `SUM([Amount])`, `AVG([Score])`, a date by `YEAR`, `QUARTER`, `MONTH`, `WEEK` or `DAY` (`QUARTER([Close date])`), `AUTO([Date])`. Conditions are `{field, operator, value}`, `value` always present: a state, select, relation, text or true-or-false field takes `is in` or `is not in` with a list (`["Won"]`, `["true"]`), and `exists` or `does not exist` with `null` ("has a Close date"); a number `equals`, `greater than`, `less than`, `equals or greater than`, `equals or less than`; a date `range` (`LAST 90 DAYS`, `THIS QUARTER`, `BETWEEN 8 WEEKS AGO AND TODAY`) or `exists`. Fibery's reports guide lists the rest.

**What the calls return**, for fix scripts and calls beyond the templates:

| Call | Result |
|---|---|

## 9. Troubleshooting

| What happened | What to do |
|---|---|
| "time is up … run this script again" | Not a failure: the script stopped before Fibery's cut-off. Send it again at once, as it is. |
| "connection lost" or "The upstream server is timing out" with no logs, a timeout or a rate limit | The script ran about a minute, or Fibery was busy. It has usually finished, or stopped part-way: wait half a minute and send the same script again, alone in its message; it does only what's missing and logs the step as a first run would. Send the next scripts one at a time until one returns. |
| Every script fails whole with "invalid response from the upstream server" or "JS Executor is down" | Fibery's script service is down, while direct calls may still work. Wait a minute or two and send one script at a time until one returns; nothing is lost, and nothing is deleted to start over. |
| A `TypeError` or "is not defined" | A typo or an unexpected result: log the result's keys (`Object.keys(r)`), fix the script, run it again. |
| "STOP, a Space with this name holds other databases" | The name is taken by a Space this build didn't make. Choose a free one ("Hiring 2"), update the design and run script 1 again; nothing was created, and `design.md`'s Assumptions name the Space you chose. |
| A `fixLogs` line | "Add default format…" on a number field and "Added field title…" on a view are Fibery's defaults. A renamed Space or database means the name you sent doesn't exist yet or is misspelled, and Fibery matched another one: stop. A field it created on an existing database is the build's mistake: show the person exactly what landed where, and remove it with `delete_fields` once they say yes. |
| "STOP, create_schema: Nothing was changed. Fix these and call again" | Nothing was made. Each line names a database or field and what to fix (a name with a slash, an inverse its target already has, a target that doesn't exist): fix the data, and the design when a name changes, and run script 1 again. Another message after "STOP, create_schema" is a call that failed: run script 1 again as it is. |
| "Last tab cannot be deleted" | Every chart of a report was rejected, so its default tab is its only one: fix the charts' conditions (§8) and run script 3 again; it adds the missing tabs, then removes the default one. |
| `Invalid input` on `query`'s `q/select` | A collection selected as a path, or a sub-query whose `q/from` is a list: §4. |
| A view is rejected | Every id in its filters must be real, and each node type must match its field (§8). "Unable to find axis config for …": every database in `items` needs its own `x` (and `y`) entry. |
| A formula is rejected or comes back wrong | §2: a sharper description, or the exact expression. A wrong type means delete and recreate, and a recreated field is a new one: every view and report that used it is built again, the report's chart as much as the view's columns. |
| An automation is rejected | A state or select value: the id from `enumIds`, not the name. An action that "doesn't exist": the error lists the ones there are, and `display_automations_schema` for that database gives their arguments. A formula value rejected or broken: §5. |
